# AI 协作与 Figma 原型约定

## 1. 目的

让 AI 按已确认的产品和工程约定协助分析、设计、生成页面或代码；遇到业务未知时先提问，不把猜测写成需求。产品事实以[产品说明](../product/product-spec.md)为准，技术选型状态以[技术栈清单](./technology-stack.md)为准。

## 2. 信息状态标记

文档、计划、原型说明和 AI 回复使用以下状态，避免把推测误认为决策：

| 标记 | 含义 | AI 的处理方式 |
| --- | --- | --- |
| 已确认 | 用户明确认可或正式资料已核实 | 按该约定继续；变更时先说明影响 |
| 建议 | 有理由的默认方案，尚未由用户定案 | 可以比较取舍，不得描述成既定要求 |
| 待星辙确认 | 依赖甲方业务、接口、账号或生产环境 | 列出问题和影响；不伪造接口或能力 |
| 待用户确认 | 产品体验、权限或技术选择尚未决定 | 一次聚焦一个影响决策的问题，给出易懂选项和推荐理由 |
| 本地模拟 | 仅供开发联调的替代服务或虚构资料 | 明确隔离环境；不得进入生产功能或冒充真实数据 |
| 原型示例 | 为展示版式而使用的虚构界面内容 | 在 Figma 页面/画板注释中标记，不作为产品字段依据 |

## 3. 需求梳理和实施

- 新功能、页面、业务流程或系统行为发生变化前，先梳理目标用户、任务、字段、状态、权限、异常和验收结果。
- 业务含义会影响资金、权限、退款、通知或状态时，先向用户说明不同方案的后果，并询问真实选择；不要连续抛出一长串术语问题。
- 多模块或多步骤实现前，先形成可审阅的设计/开发计划；明确依赖、风险、文档更新点和仍未决定的内容。
- 新业务模块编码前，先建立对应架构设计，记录模块职责、流程、状态、接口、幂等、失败恢复和安全边界；真实外部字段需来自正式接口资料。
- 方案、字段或页面内容不在现有已确认资料内时，使用“建议”“待确认”或“本地模拟”标注；必要时先问用户，不以技术方便替用户决定业务。
- 完成实现后更新与实现相关的架构、技术、目录或运维文档，避免代码与说明脱节。

## 4. Figma 页面生成约定

### 4.1 生成前需要什么

开始一个 Figma 页面前，先确认页面服务的用户任务，并读取相关产品说明、对应模块架构（若已有）、视觉原则、视觉参考和视觉样式规范。利用现有设计系统和组件，保持可编辑的图层与组件结构；Figma 页面不能只交付一张扁平截图。

页面所需字段必须有产品需求、已确认架构/API 契约或用户明确确认作为依据。若数据契约尚未形成，先用不具业务承诺的占位布局进行设计，或向用户确认字段清单；不得因为后台页面常见而自行加入邮箱、地区、支付渠道、风控结论等字段。

### 4.2 原型数据标注

- 画板或明显的原型注释标明“原型示例数据（非真实交易）”。
- 示例订单号、金额、姓名、时间和状态使用明显虚构值；不放真实客户信息、商户密钥、卡号或生产交易截图。
- 原型中未确认的字段标注“待确认”，而不是伪装为正式字段。
- 该标记仅用于设计稿和开发交接；不得据此在生产运营后台新增“测试/模拟”字段、入口或开关。
- 页面验收时逐项核对产品字段；没有依据的字段从交付稿移除或先请用户确认。

### 4.3 页面评审和开发交接

- 先评审任务路径、信息层级、字段、空态、加载态、错误态、权限态和窄屏布局，再评审细节样式。
- 以产品视觉原则避免模板化 AI 页面：使用明确的视觉层级、克制的颜色和真实业务密度；组件库提供交互基础，不决定最终视觉。
- 交接开发时附上画板链接、使用的组件/令牌、交互状态、字段来源和所有待确认项。
- 若 Figma MCP 或目标文件不可用，先给出可审阅的页面结构与字段清单，不声称已生成 Figma 文件。

## 5. 工具与 MCP 使用边界

根据任务使用适用的 Superpowers 技能、Figma 技能或 MCP；工具服务于需求澄清、设计、实现和验证，不是每轮对话的形式步骤。读取参考资料、生成页面或执行会改变外部状态的操作前，确认对象和目标明确。支付实现的外部协议以正式文档及沙盒/生产实际能力为准。

工程验证仅供开发者和上线准备使用。不得把单元测试、静态检查或沙盒联调扩展成面向星辙员工的产品内测试交易功能。
