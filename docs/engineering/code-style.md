# 个人代码风格与通用工程约定

## 1. 适用范围

本文集中记录跨语言的个人偏好和通用写法，避免每个规范重复描述。Java 细则见 `backend/java.md`；React/TypeScript 细则见 `frontend/react-typescript.md`；Tailwind 和视觉实现规则见 `frontend/visual-style.md`。

## 2. 基本编码理念

- 代码简洁易读、变量和函数命名语义清楚。
- 先选择满足需求的最简单方案，不为了展示技术而引入复杂模式。
- 函数职责单一，重复逻辑在存在稳定复用后再抽取。
- 不写临时凑合的 Hack；确需兼容或绕过限制时，说明原因、影响范围和移除条件。
- 兼顾边界场景、失败处理和长期维护，但不预先构建没有需求支持的框架。
- 优先遵循项目已确认的架构、语言规范和依赖版本；新旧写法不一致时先说明再调整。
- 修改聚焦当前需求，不附带无关重构。

## 3. JavaScript 和 TypeScript 函数写法

- **箭头函数作为前端默认写法**：React 组件、回调、事件处理器、Hook 内局部函数优先使用箭头函数。
- 示例：

```ts
const TransactionSummary = () => {
  const visibleRows = rows.filter((row) => row.isVisible)
  return <TransactionTable rows={visibleRows} />
}
```

- 普通 `function` 声明仅在函数提升有实际价值、需要生成器语法、库/API 强制特定形式，或箭头函数明显降低可读性时使用。
- 不为统一形式把每个短回调都写成冗长函数体；也不为追求箭头写法牺牲递归、命名和调试清晰度。
- React 函数组件不依赖实例状态；通过 props、Hooks、Context 和明确的返回值传递依赖。
- Java 使用语言习惯的类、方法和构造器写法，不把 JavaScript 箭头函数偏好机械套用到 Java。

## 4. 模块化偏好

- 按业务职责划分模块，例如交易、退款、通知、对账、账号和操作审计。
- 模块拥有自己的页面、接口类型、React Hooks 和后端用例；只暴露其他模块需要的稳定接口。
- 小模块不为目录树完整而拆出大量空文件；代码达到职责混杂或多个功能真实复用时再拆分。
- `shared`、`common`、`utils` 不作为默认收纳处；只有稳定、跨模块的能力才进入共享层。
- 前后端分别保持业务模块边界；前端页面不直接承担后端领域规则，后端 Controller 不直接承担核心业务流程。

## 5. 命名与注释

- 命名使用业务词汇而不是笼统技术词；避免 `data`、`info`、`manager`、`handler` 作为唯一语义。
- 布尔值用 `is`、`has`、`can` 等表达状态或能力；事件处理函数用动作动词。
- 注释解释“为什么这样做”、外部协议限制或容易误改的边界，不复述显而易见的代码。
- TODO 必须附带需要解决的问题和适用条件；未经用户确认不能用 TODO 作为交付替代。

## 6. 异常和边界处理

- 在系统边界校验外部输入，内部模块传递经过类型和业务约束的模型。
- 不吞掉错误；只有能恢复、转换或补充上下文时才捕获异常。
- 对外错误给出可理解且不泄露敏感信息的提示；内部日志保留足够的关联标识用于排查。
- 对支付结果未知、网络超时、通知重复和退款重试等情况采用明确状态，不靠猜测成功/失败。
- 金额、币种、权限和状态转换由后端权威校验；前端校验只改善交互。

## 7. AI 协作要求

- 编码前先拆解需求，识别业务边界和未决事项，说明关键风险与方案取舍。
- 面对未知业务规则，一次聚焦一个关键问题询问，不自作主张补全甲方决策。
- 涉及架构或外部接口的较大改动，先写架构设计文档并由用户审阅。
- 输出代码前检查命名、重复逻辑、依赖新增、异常路径和与相关规范的一致性。
