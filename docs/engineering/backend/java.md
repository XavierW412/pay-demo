# Java 后端开发规范

## 1. 适用范围

本文约束支付项目后端 Java 代码的目录、分层、命名、业务处理、安全和质量检查。

- 当前技术选型状态见[技术栈清单](../technology-stack.md)；其中建议项尚需用户确认。
- 后端目标形态：单体部署、按支付业务模块组织，不拆微服务。
- 项目目录和模块名称见[工程目录结构规范](../directory-structure.md)。

## 2. 总体开发要求

1. 先还原当前业务规则、状态和外部契约，再编写代码；不凭空增加业务决定。
2. 代码优先清晰和可维护，避免炫技式抽象、重复框架和一次性临时代码。
3. Controller 保持轻量，业务规则不散落在 Controller、数据库实体、定时任务或第三方适配器中。
4. 每个类、接口、方法有明确职责；命名反映支付业务含义。
5. 新依赖、并发策略、缓存、消息组件和跨模块抽象需要说明真实问题及运维影响。
6. 金钱、状态、权限、幂等、审计和错误处理按本文约束实现；不能以“沙盒代码”为由省略生产必需的安全边界。

## 3. 项目结构和模块职责

### 3.1 单个业务模块内部

按项目实际使用的包结构逐步建立以下职责；不强制创建空包。

```text
payment/
├── interfaces/        # REST Controller、请求/响应 DTO
├── application/       # 用例、事务边界、模块协作
├── domain/             # 状态、业务规则、值对象和领域事件
└── infrastructure/   # Repository、外部 API、任务和配置实现
```

- `interfaces` 接收和转换传输数据，做请求格式校验，调用用例并构造响应。
- `application` 编排一次完整用例，不重复实现领域不变量。
- `domain` 表达支付和退款状态转换、金额约束和业务不变量，不依赖 Spring Web 或数据库实现。
- `infrastructure` 实现数据库、Airwallex、星辙、任务调度和其他外部技术接口。

### 3.2 首期业务模块

- `order`：保存星辙订单必要引用和接入信息，不接管星辙商品、订单审批、订阅或服务开通。
- `payment`：管理本项目的支付单、创建收款和支付状态核实。
- `refund`：执行星辙已批准的退款指令，不批准退款。
- `notification`：管理向星辙的支付/退款通知、回执和重试状态。
- `reconciliation`：核对订单、支付、退款和结算记录，保留差异证据。
- `operations`：运营后台查询、按权限进行通知重试和异常备注。
- `identity`：员工登录、邀请和角色授权。
- `audit`：记录重要人工操作和关键系统操作。
- `integrations.airwallex`、`integrations.starpath`：隔离服务商协议和甲方接口。

### 3.3 依赖规则

- 依赖方向为接口层 → 应用层 → 领域层；基础设施实现应用/领域定义的端口。
- 模块不得直接读取其他模块的 Repository、数据库实体或私有表；通过明确的应用接口协作。
- 模块间不能形成循环依赖；共享代码进入 `shared` 前，要证明该概念稳定且被多个业务模块真实使用。
- Airwallex 适配器转换外部 API、Webhook 和错误；支付模块不能依赖 Airwallex 专属 DTO。
- 本地模拟星辙和正式星辙实现同一个内部接入契约；生产配置不得加载模拟实现。
- DTO、领域对象和持久化实体分离。实体不直接从 Controller 返回，也不作为请求体接收。

## 4. Java 语言与格式

- 使用 Java 21 语法能力；禁止为旧版 Java 兼容而编写无必要的旧式样板代码。
- 包名全小写；类和接口使用 `UpperCamelCase`；方法、字段和参数使用 `lowerCamelCase`；常量使用大写下划线。
- 类型和方法名称说明业务职责，避免 `CommonManager`、`DataProcessor`、`Util`、`Info` 等宽泛命名。
- 优先使用构造器注入，禁止字段注入；依赖应为 `final`，便于明确对象所需能力。
- DTO 优先使用 `record` 表达不可变数据；包含行为和生命周期的领域实体使用普通类。
- 不依赖 Lombok 隐藏重要构造和行为；只有收益明确时再讨论引入。
- 格式由 Spotless + Google Java Format 固定；本地格式与 CI 校验采用同一配置。
- 导入语句分组和静态导入遵循格式工具；不手工维护与自动格式化冲突的个人风格。
- 注释说明业务原因、边界或外部协议，不逐行复述代码。

## 5. Spring Boot 实现规则

### 5.1 Web 和接口

- Controller 只负责绑定请求、基础格式校验、调用用例和返回响应；不直接调用 Repository 或第三方 HTTP 客户端。
- API 请求 DTO 与响应 DTO 独立定义；外部契约字段经显式映射进入内部模型。
- 使用 Jakarta Bean Validation 做字段必填、格式和长度校验；金额、币种、原交易关联和权限等业务校验仍在用例/领域层完成。
- API 响应统一包含可识别的业务数据或稳定错误码；不把 Java 异常类型、堆栈或服务商原始报文暴露给前端。
- URL、HTTP 方法和状态码表达资源与动作；副作用动作不伪装成查询请求。
- Controller 解析到的用户身份和角色必须由服务端安全上下文提供，不能信任前端提交的角色字段。

### 5.2 依赖注入、配置和事务

- 使用构造器注入；组件范围由 Spring Bean 管理，不在业务代码中随意 `new` 依赖实现。
- 配置通过类型安全配置对象绑定和校验；不得在源代码中硬编码域名、密码、API 密钥或通知密钥。
- 开发、沙盒和生产配置显式区分；密钥由运行环境安全注入。
- 事务放在应用用例边界或明确的领域操作边界，不在 Controller 中开启事务。
- 避免长事务包住 Airwallex 或星辙网络请求；数据库事务与远端请求不能视作同一个原子操作。
- 事务中的外部副作用通过已设计的幂等和可恢复步骤衔接；必要时采用事务 Outbox，但只有确认需求后才实现。

### 5.3 数据库访问

- 使用 Spring Data JPA/Hibernate 处理常规聚合持久化；复杂查询可以使用明确的 JPQL、Criteria 或 SQL，并注明用途。
- Repository 面向单一模块内部；不提供跨业务模块随意查询其他模块表的通用入口。
- 状态字段采用稳定字符串枚举映射，不依赖 Java 枚举的序号。
- 关键唯一性、外键和金额边界应尽量有数据库约束作为最后保护。
- 对可能被并发更新的支付/退款状态，定义乐观锁、唯一约束或原子更新策略；不得只靠内存判断防重。
- 生产结构变化通过 Flyway 版本迁移；迁移应可审查、可重复，不在应用启动时无条件重建或清空生产表。
- 大量关联查询需关注 N+1 和分页行为；在证明有性能问题后再优化，保留正确排序和一致性语义。

## 6. 支付与金额编码规则

- 金额使用 `BigDecimal`，禁止 `float`、`double` 和二进制浮点金额运算。
- 币种存为明确的 ISO 4217 代码并跟金额一起传递；金额精度、舍入和最小单位以外部协议及币种规则为准。
- 不依赖 `BigDecimal.equals` 比较数值大小；比较金额时使用 `compareTo`，并显式定义尺度处理。
- 订单金额、支付金额、退款金额、结算金额分开记录；不得覆盖原始请求以隐藏差异。
- 用户浏览器返回页面不能将支付置为成功；必须按确认后的 Airwallex 服务端通知、验签、查询等流程核实。
- 支付状态、退款状态、通知状态、结算状态分别建模；“支付成功”不等于“已结算”。
- 状态修改必须遵守允许的转换路径；未知结果保留待核实状态，不推断为成功或失败。
- 操作历史记录操作者、时间、对象、动作、前后状态、结果和必要关联编号；审计记录不能被普通操作覆盖。

## 7. 幂等、并发和外部集成

- 支付创建、退款指令、Webhook 事件和星辙通知使用稳定幂等标识，并通过数据库唯一约束防止重复副作用。
- 幂等记录包含请求关联键、处理结果和可恢复状态；同一请求重试返回已有结果或当前处理中状态。
- 远端超时视为“结果未知”，先通过服务商查询或幂等重试确认，不能直接再创建一笔不同收款。
- 重试只用于明确可安全重试的操作；设置上限、退避间隔、记录下次执行时间和最终失败原因。
- 对外 HTTP 调用设置连接、读取和整体超时；异常信息不包含密钥或完整敏感响应体。
- Webhook 校验签名时使用官方定义的原始请求内容和算法；拒绝无效签名，按事件 ID 防重，并记录验签和处理结果。
- 外部调用和本地交易记录之间存在失败窗口时，显式设计补偿/核对流程；不要以“catch 后再试一次”代替一致性设计。
- Airwallex API DTO、星辙请求 DTO 与项目领域对象分开；变更外部字段不应迫使内部支付规则随之变化。

## 8. 安全、日志和错误

- 使用 Spring Security 在服务端实现身份验证和角色授权；所有者只读权限从 API 层和用例层落实。
- 密码使用 Spring Security 提供的安全密码编码器；不自制加密算法，不明文保存密码。
- 登录、邀请、会话失效、跨站请求和 Cookie 安全属性按最终域名部署方案配置。
- 日志采用 SLF4J 参数化记录，不用字符串拼接大量对象，不捕获后静默忽略异常。
- 全局异常处理返回稳定错误码和安全消息；日志保存异常上下文和请求关联号。
- 严禁记录 Airwallex/星辙密钥、认证令牌、完整卡号、完整 Webhook 签名和不必要个人信息。
- 外部原始响应需要排查时，只记录脱敏后的必要字段，并限制访问和保留时间。
- 权限拒绝、重复请求、验签失败、状态不一致和通知重试失败都要可查询、可审计。

## 9. 测试约定

- JUnit 5 用于领域规则、金额运算、状态转换、幂等和异常分支。
- Spring Boot Test/MockMvc 用于接口绑定、校验、授权和错误映射。
- Mockito 用于隔离 Airwallex、星辙和时间等外部边界；避免 mock 本模块内部所有调用造成实现细节测试。
- Testcontainers 用于确实依赖 PostgreSQL 语义的集成测试，保证本地和 CI 使用一致数据库行为。
- 对支付、退款、Webhook、通知重试和对账差异至少覆盖成功、重复、超时未知、失败和并发边界。
- 测试数据必须虚构；沙盒凭证通过本机忽略配置注入，不把真实密钥写进测试资源。
- 每个缺陷修复补充能复现该缺陷的验证；测试优先断言外部可观察结果和资金状态。

## 10. 提交前质量检查

根据仓库建立的 Maven Wrapper 脚本，CI 至少执行：

1. Spotless 格式检查。
2. Checkstyle/SpotBugs 中已启用的静态规则。
3. 编译和类型检查。
4. 单元测试和必要的集成测试。
5. 应用打包。

脚本名应记录在 README；禁止要求开发者依赖未固定的全局 JDK、Maven 或本地数据库版本。
