# 开发路线图

## 1. 使用方式

本路线图安排推进顺序，不虚构日期或未确认的外部契约。每个阶段开始时，围绕具体功能补充架构设计和可执行的详细计划；需要业务选择时先询问用户。阶段完成后同步更新相关文档和路线状态。

状态：

- **已完成**：已存在并完成本阶段所列内容。
- **进行中**：当前正在完善。
- **待开始**：前置条件尚未满足或尚未实施。
- **待外部确认**：等待星辙、Airwallex 账户或生产平台资料。

## 3. 阶段说明与进入条件

### 阶段 0：文档与仓库基线

**目标：** 让后续开发有清晰入口、规则和可追溯历史。

**产物：** 产品说明、技术栈、代码规范、目录规范、前端视觉规范、架构维护规则、部署原则、AI/Figma 协作规则、路线图和首个 Git 提交。

**完成条件：** 新参与者能从 `README.md` 和 `AGENTS.md` 找到适用规范；文档链接有效；工作区无未提交基线文件。

### 阶段 1：产品问题收敛

**需要讨论：** 订单重复/过期、订单状态未知、运营人员角色和操作权限、异常告警对象、记录导出与对账频率。星辙资料未到时，可保留清晰的本地模拟契约，但必须标为模拟。

**进入阶段 2 的条件：** 目标页面用户、工作任务和首期展示数据字段已经能逐项追溯到产品需求；剩余未知字段明确标成待确认。

### 阶段 2：页面与视觉方向

**建议的首个页面：** 交易列表，因为它能验证运营后台的信息密度、筛选、状态区分和整体设计方向。它只是建议，开始生成前仍会询问用户是否接受，以及字段清单是否完整。

**Figma 约束：** 使用项目的视觉规范和设计系统生成可编辑页面；原型中的虚构数据标注“原型示例数据（非真实交易）”。不在产品稿中增加未经确认的字段，也不添加生产测试入口。

### 阶段 3：技术方案与项目骨架

**前置：** React 与 shadcn/ui 目前是建议方向，需在初始化项目时确认可用稳定版本；Java、Spring Boot、PostgreSQL 及运行平台也要在创建工程配置前锁定版本和兼容关系。

**产物：** 前端和后端最小可运行骨架、配置隔离、数据库迁移机制、本地启动说明、模拟星辙的开发边界。开发环境模拟器不得进入生产配置。

### 阶段 4—8：支付业务模块

每一模块编码前独立补齐对应架构和详细开发计划：

1. 支付创建与 Airwallex 托管收银台。
2. Airwallex 事件/查询核实、支付状态和星辙通知重试。
3. 后台账号、只读项目所有者、操作权限、审计和异常处理。
4. 星辙批准的退款指令、部分退款边界及防重规则。
5. Airwallex 结算数据来源、对账匹配与差异跟进。

外部接口、状态、权限或金额规则依赖星辙/账户资料时，不因路线图存在就推定资料已确认。应把未知契约列清，先使用明确隔离的开发替身推进不依赖部分。

### 阶段 9：生产准备

**前置：** 星辙生产 API、Airwallex 商户账户与币种能力、部署区域和资源负责人、域名与 HTTPS、密钥注入方式、告警与备份恢复方案已确认。

**完成条件：** 沙盒联调与生产配置隔离明确；真实支付、支付状态、退款、通知、对账及故障恢复责任经星辙验收；生产运营界面没有测试交易功能。

## 4. 文档随着实现持续演进

- 新业务模块先在 `docs/architecture/` 写设计，再写对应详细开发计划。
- 技术版本或依赖变更更新技术栈和构建配置。
- 字段、权限和业务规则变化更新产品说明及页面稿。
- 真实接口资料到达后，在 `docs/integrations/` 或对应架构文件记录正式契约，不用模拟字段覆盖正式协议。
- 模块实现后记录实际状态机、重试、恢复、审计和已验证范围。
- 此路线图不替代每个模块开始前的设计评审，也不意味着所有功能一次性交付。
