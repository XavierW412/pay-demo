# 支付项目范围校正与代码整理建议

## 1. 状态与目标

2026-10-09 根据用户提供的甲方聊天记录、已确认产品定位和当前源码完成本次静态核对。本文保留原静态审计与整理依据；截至本轮实施，模拟签名、同订单重试、托管跳转、核心核实与自动补查均已调整，详见下方实施记录。功能验收和生产就绪不由静态审计替代；保留业务数据与历史迁移。

目标链路：开发用星辙模拟系统创建真实模拟业务订单 → 支付项目处理正式形态的接口与支付逻辑 → Airwallex 沙盒创建收款并托管付款 → 支付项目核实并通知模拟星辙 → 模拟星辙开通示例服务。生产替换外部对接和环境配置，复用支付核心。

“模拟”主要发生在星辙业务及其接口。本项目仍通过官方沙盒接口完成收款请求、查询、退款与通知处理，不采用前端按钮或伪造响应宣告成功。沙盒不使用真实资金，不能据此宣称生产支付能力相同。

## 2. 保留、调整和移除候选

| 当前内容 | 建议 | 理由 |
| --- | --- | --- |
| 后端 `payment`、Airwallex 认证及收款网关 | 保留并完善 | 接收业务订单、维护支付记录、真实调用沙盒是交付核心 |
| 星辙请求认证、Webhook 验签去重、通知队列 | 保留并完善 | 中转工具仍需可靠执行与留痕，不能只做页面跳转 |
| `refund` | 保留 | 接收星辙批准指令、金额保护、执行和结果核实符合范围 |
| `operations` 与审计 | 保留 | 流水查询、员工异常操作和所有者只读已明确需要 |
| `reconciliation` | 保留，准确称为支付状态核查 | 当前核查不等于完整结算对账，不能删掉差异记录或假装已结算 |
| 前端 `mock-xingzhe`、后端 `simulator` | 保留为开发工具 | 无真实星辙资料时承担外部替身，不属于正式支付产品 |
| `CheckoutPage.tsx` 的摘要、Drop-in、组件加载及付款交互 | 改为最小托管跳转衔接；替换完成后移除内嵌交互 | 自有收银台已不在交付范围，不应继续扩展 |
| `CheckoutReturnPage.tsx` | 简化为必要的返回衔接，主要结果回到星辙订单页 | 浏览器返回不负责确认资金状态，不需要发展成支付项目用户中心 |
| `checkout` 后端 | 按依赖调整，不能整包删除 | 令牌/跳转上下文可能继续需要；主动核实还被运营操作引用 |
| SDK 与付款上下文接口 | 按所选托管方案保留必要部分 | 使用官方 SDK 跳转方案时仍需 SDK 和安全上下文，移除 Drop-in 不代表可同时删除全部依赖 |
| Flyway 迁移、交易/通知/退款/审计数据 | 保留 | 页面范围调整不应抹去支付关联、历史或已应用迁移 |
| 旧内嵌收银设计和计划 | 标记历史、已被新范围取代 | 避免后续代理按旧计划恢复自有收银台 |

模拟器仅保留服务选购、订单查询、根据可信通知模拟开通、星辙批准退款和接收结果。没有必要重建真实 GIS、完整客户管理或其他星辙业务。继续保持本地后端 profile 隔离和前端正式构建入口隔离；不为隔离要求额外重构成多个微服务。

## 3. 已发现的问题与待完善的调用边界

### 3.1 模拟付款请求使用了错误方向的密钥

`LocalMockPaymentOrderClient` 使用 `startrail.integration.outbound-secret` 签名创建付款请求，而 `IntegrationPaymentOrderController` 使用 `inbound-secret` 验证。当前本地默认两者都为同一个开发值，错误可能被掩盖。应让模拟星辙发起付款使用入站契约密钥，模拟星辙接收结果使用出站密钥；以不同开发密钥检查两个方向，不能把生产密钥合并为一把。

### 3.2 核实能力不应从属于用户付款页

`OperationsPaymentActionService` 依赖 `CheckoutStatusRefreshService`，并调用其按支付单核实方法。后续应把与页面令牌无关的核实/状态更新职责放回支付应用层，页面或跳转控制器、后台和补查任务调用同一核心能力。移除用户页面时不能删掉服务端核实、字段校验或通知入队。

### 3.3 漏回调的自动补查尚未闭合

当前 Webhook 处理器只处理已经入库的事件；主动状态更新来自付款返回页或员工操作。定时 `PaymentReconciliationService` 保存差异，不自动更新状态。因此“回调未送达且用户关闭页面”场景尚缺不依赖浏览器的支付补查恢复任务。建议对未决支付单定时查询，经过同样订单核验后更新状态并通知星辙；差异核查模块继续保存观察证据，不将发现差异等同于自动批准业务操作。

### 3.4 托管入口与返回地址待实施

当前收款响应是支付项目相对路径，模拟前端直接用路由跳转。正式对接应明确星辙拿到的入口是哪个可访问地址、返回星辙的地址如何受控配置、链接期限和过期恢复方式。收款创建也需按托管方案补齐必要的返回参数，不能硬编码正式环境到模拟页面。

### 3.5 模拟订单失败恢复需要更接近正式交互

当前模拟器先保存业务订单，再调用支付创建；失败后界面再次点购买会创建新的业务订单。应在原业务订单上展示未完成的支付发起，并用稳定请求标识安全重试，避免模拟器用不断新建订单掩盖幂等和超时恢复问题。正式取消、过期、金额变更和多次尝试规则仍需星辙确认。

### 3.6 报表与完整对账待补齐

当前已能查看交易、退款和支付核查差异。尚需按星辙确认的统计口径补充流水报表，并分别接入星辙订单/业务回执和 Airwallex 结算报告。支付结果、通知送达、服务开通和结算是四件不同的事。

## 4. 托管方案的建议

优先沿用现有 Payment Intent 核心，以官方 SDK 的托管跳转能力替换内嵌组件，保留最小衔接。这样不必为了收银展示变化重写支付、退款和通知关联。

Airwallex 另有不需要前端 SDK 的 Checkout Session 托管方案，但截至本次核对，官方快速入门标记为早期开放，并依赖商品/价格引用；还涉及新的支付关联生命周期。因此不因为“没有前端代码”就立即迁移，更不引入由支付工具管理星辙商品价格的额外职责。具体实现需在托管衔接设计中最终确定。

官方资料：[托管收银台及 SDK 跳转](https://www.airwallex.com/docs/payments/integration-options/web-checkout/hosted-payment-page)、[Checkout Session 早期开放说明](https://www.airwallex.com/docs/payments/integration-options/web-checkout/checkout-session/quickstart)、[沙盒环境](https://www.airwallex.com/docs/developer-tools/sandbox-environment)。

## 5. 建议开发顺序

1. 修正模拟对接的双向密钥和同订单重试，整理提议契约及接口样例。
2. 把内嵌付款页改成托管跳转衔接，配置受控返回星辙地址；确认引用后移除不用的内嵌代码。
3. 将服务端支付核实从页面模块解耦，补齐漏回调、浏览器关闭、网络超时后的恢复。
4. 完成沙盒创建、实际付款、后台核实、可靠通知、模拟星辙开通的闭环；当前账户可用方式另行确认。
5. 完成星辙退款指令到沙盒退款结果的闭环，完善必要报表及异常处理；按拿到的资料推进订单与结算对账。
6. 用正式星辙资料适配接口和认证，准备生产账户、地址、资源与运行配置，再完成真实场景验收。

主代理负责架构、计划、沟通和审阅；实现任务按用户指定交给 `gpt-6-luna` 子代理。本文阶段只做范围审计，不派发删代码任务，不提交。

## 6. 哪些可以通过配置替换，哪些仍需对接

| 项目 | 预期变化 |
| --- | --- |
| Airwallex 沙盒到生产 | 凭证、接口环境、Webhook 验签密钥、收银环境、回调/返回域名、账户实际能力分别核对 |
| 模拟星辙到真实星辙 | 接口地址、字段映射、签名/认证、状态映射、通知回执与业务订单查询按正式协议适配 |
| 本地到正式部署 | HTTPS、数据库、会话/账号、监控、备份和运行资源配置 |
| 支付核心 | 订单关联、金额校验、幂等、状态核实、退款执行、通知和留痕尽量共用，避免沙盒成功逻辑另写一套 |

目标是减少上线时核心改动，而不是承诺只换两把密钥即可上线。只有正式星辙接受当前提议契约且账户能力满足要求，外部适配才可能主要成为配置替换。

## 6. 本轮实施记录

- 已使用付款入站密钥签名模拟星辙请求；创建业务订单与发起收款分离，付款失败后可在原订单用原请求编号重试。
- 已移除内嵌付款交互，使用锁定 SDK 的官方托管跳转，创建响应返回公开绝对入口，业务返回地址来自可信服务端模板。锁定版本不发送未声明的取消参数。
- 核实能力已移至支付应用层，运营直接调用核心；新增 V110 自动补查游标、单笔租约、批次上限和失败退避。
- 状态更新和通知同事务；关联创建响应不覆盖已核实状态，成功/取消不会被旧观察回退。原交易、退款、核查、权限与审计模块保留。
- 正式星辙契约、商户开通、真实沙盒付款/退款与资金结算仍按路线图推进；本轮不扩大为自有收银台或结算产品。
