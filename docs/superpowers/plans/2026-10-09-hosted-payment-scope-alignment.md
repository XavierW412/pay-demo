# 托管收银台与支付中转范围校正实施计划

> 实施代理按 Superpowers 子代理开发流程逐项实现。用户已认可范围校正建议并明确授权继续实施；主代理安排、审阅，代码使用 `gpt-6-luna`。不重复要求确认，不提交，不增加或运行测试；编译、静态检查和已授权的本地接口联调分别记录证据。

**目标：** 用开发用星辙模拟器和真实 Airwallex 沙盒跑正式形态的支付中转链路，使用托管收银台并使结果恢复不依赖浏览器。

**架构：** 保留 Payment Intent、退款、通知、核查和运营模块。模拟星辙只经过签名 HTTP 接口调用支付服务；现有 `/checkout/{token}` 收缩为官方 SDK 托管跳转，付款资料在 Airwallex 页面收集。支付核实下沉到支付应用层，定时补查和运营操作复用它，差异核查继续只留证据。

**技术：** Java 21、Spring Boot、PostgreSQL、React、TypeScript、Airwallex Components SDK；不增加依赖、不改变已锁定版本。

**依据：** [范围校正建议](../../roadmap/scope-alignment.md)、[产品说明](../../product/product-spec.md)。托管沿用官方 SDK 跳转，不引入早期开放的 Checkout Session 和商品价格管理。

## 全局约束及审阅重点

- 保留已有未提交代码、交易、退款、通知、审计和已应用迁移，不整包删除付款模块。
- 模拟器只启用在本地，正式运行不暴露模拟接口；金额币种来自星辙服务端，国家独立提供。
- API key、商户认证、Webhook 密钥不进入前端、日志或 Git；本次付款的客户端上下文通过短期令牌获得。
- 浏览器跳回、关页、超时不代表成功或失败；只有服务端核验字段及状态后更新和通知。
- 请求超时用同一业务单和请求标识重试；迟到通知不能被模拟器旧快照覆盖。
- 正式跳转入口及业务返回地址必须来自可信配置，不能接受浏览器任意 URL；本地固定为模拟订单页，正式由星辙提供。
- 定时任务有单笔租约、有限批量、退避及失败隔离；终态不从旧回调回退，不重复通知。

**范围：** 新增支付应用层核实服务/状态应用服务；现有 checkout 核实适配器与运营调用；支付补查调度、独立迁移（公共下一序号 `V110`）。不改任务 2 的上下文及状态响应类。

- [x] 将按支付单核实、15 秒限频及核验后通知职责放回支付核心；令牌刷新只是薄适配器，运营直接依赖核心。
- [x] 对已有外部支付单的未决内部状态进行后台补查；单轮最多 10 笔、单笔有租约、查询失败隔离及退避，先观察至少 60 秒，周期至少 60 秒。
- [x] 核实仍走现有字段匹配和行锁，仅状态变化入通知队列；成功、取消不自动从旧观察回退；FAILED不冻结后续可信核实成功的能力。
- [x] 不把差异核查改成自动操作器；定时补查恢复是单独责任。没有外部支付单的创建恢复继续使用相同创建请求编号。
- [x] 构建后检查后台调用依赖和迁移序号，保留历史迁移与已有数据。

## 实施决定与取舍

- 沿用现有 Payment Intent 和锁定 SDK 托管跳转，避免引入早期开放 Checkout Session 的商品/价格职责；若之后需要纯服务端直链，再单独评估迁移生命周期。
- 锁定 SDK 类型未声明通用取消参数，因此不强行扩展类型；成功地址及认证返回地址相同。直接退出托管页面仍需用户返回，不能承诺统一取消按钮。
- 本轮保留非终态合法往返；只保护成功和取消终态。严格排序所有非终态通知需要正式契约的版本依据，当前不宣称完成。
- 本轮不提交、不清理历史脏工作或数据、不新增或运行测试；用户要求的本地接口联调与编译证据单独记录。
