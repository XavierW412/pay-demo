# 星辙订单国家/地区信息传递设计

## 文档状态

- 状态：用户已确认方向，已按计划实施
- 范围：本地星辙模拟接口、支付单记录、Airwallex 托管收银台上下文
- 重要声明：本文定义开发阶段的本地模拟契约，不代表星辙正式接口字段或生产业务规则。
- 关联设计：[本地星辙模拟与 Airwallex 支付链路设计](2026-10-09-local-xingzhe-airwallex-payment-design.md)
- 官方资料核对日期：2026-10-09

## 1. 要解决的问题

当前支付服务用固定配置 `AIRWALLEX_CHECKOUT_COUNTRY_CODE` 为 Airwallex 托管收银台提供国家/地区代码。这会让支付服务替星辙猜付款用户所在国家/地区，也无法让每笔订单根据实际订单信息选择对应值。

本设计把该信息作为订单上下文由星辙传入支付服务。支付服务保存订单快照，并在生成该笔收银台上下文时使用。金额和币种仍由星辙订单提供，国家/地区代码与币种分开表达。

## 2. 设计决定

1. 本地模拟星辙创建业务订单时，随订单一并发送 `shopperCountryCode`。
2. 本地模拟商品可以配置示例国家/地区：CNY 示例订单使用 `CN`，USD 示例订单使用 `US`。这只是本地样例数据的显式配置，不是“从币种推断国家/地区”的生产规则。
3. 真实星辙应按其掌握的用户/订单信息决定是否提供该字段；实际字段名和含义须以星辙接口资料确认。支付服务不自行根据币种、IP 或用户国籍推导并写入订单字段。
4. 字段允许缺省。若没有值，支付服务不向 Airwallex.js 传 `country_code`，由 Airwallex 按其托管收银台规则处理；不得回退到固定国家/地区环境变量。
5. 移除 `AIRWALLEX_CHECKOUT_COUNTRY_CODE` 固定配置，改用支付单中保存的可选国家/地区代码。
6. 国家/地区代码在创建支付单时作为请求快照的一部分参加幂等一致性比较。同一 `requestId` 若重试时更换国家/地区代码，按请求内容冲突处理。

## 3. 字段定义

本地模拟契约使用 `shopperCountryCode`，表示本次付款用户所在国家/地区的 ISO 3166-1 alpha-2 代码，例如 `CN`、`US`。它不是商户注册国家/地区，不是结算国家/地区，也不意味着该国家/地区的所有支付方式都能使用。

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `amount` | 十进制字符串 | 是 | 沿用当前金额规则。 |
| `currency` | 大写字符串 | 是 | 沿用当前首期 `CNY`、`USD` 范围。 |
| `shopperCountryCode` | 大写字符串 | 否 | 有值时为两个大写英文字母；缺省/null 表示星辙当前未提供。 |

金额币种由星辙业务订单确定；国家/地区由星辙根据其订单上下文提供。二者可以有关联，但本支付服务不把一种币种固定绑定到某个国家/地区。

## 4. 本地模拟接口变化

现有 `POST /api/v1/integration/payment-orders` 请求示例调整为：

```json
{
  "requestId": "50d86ae3-0ccf-4c89-a26a-d5c81625be10",
  "businessOrderId": "XZ-DEV-20261009-000001",
  "amount": "299.00",
  "currency": "CNY",
  "shopperCountryCode": "CN"
}
```

缺省示例：

```json
{
  "requestId": "5a4a3cef-8cd8-4bf3-a14e-10d7a78bb29a",
  "businessOrderId": "XZ-DEV-20261009-000002",
  "amount": "39.00",
  "currency": "USD"
}
```

本地商品目录显式维护每个模拟商品的金额、币种和示例国家/地区代码。这样页面上选择 USD 样例时，模拟星辙是把 `USD` 和该样例配置的 `US` 一起写入业务订单，再把订单数据传给支付服务；支付服务不根据 `USD` 自动生成 `US`。

## 5. 数据与收银台处理

### 5.1 支付单保存

- 支付单增加可空 `shopper_country_code` 字段，长度为 2。
- 创建支付单时保存经校验的请求值；没有提供时保持 null。
- 新增数据库迁移，不修改既有迁移文件。
- 同一幂等请求的订单号、金额、币种或国家/地区快照任一不同，都作为幂等冲突，不创建第二笔 Payment Intent。

### 5.2 Checkout 上下文

- Checkout Context API 的 `countryCode` 改为可选/null。
- 值存在时，前端只向 Airwallex.js 提供该支付单保存的 `country_code`。
- 值缺省时，从 Airwallex.js 初始化参数中省略 `country_code` 属性，不传固定默认值。
- 不改变金额、币种、Payment Intent、付款结果核实或星辙通知的所有权和处理方式。
- 国家/地区不会额外加入支付成功通知，除非未来确认星辙业务需要该信息。

Airwallex 托管收银台资料将 `country_code` 说明为用户国家/地区，且该字段可选；未提供时可由 Airwallex 根据用户 IP 推断。国家/地区和币种会共同影响显示的支付方式，实际可用方式仍取决于商户账户配置。详见 [Airwallex.js 托管收银台文档](https://www.airwallex.com/docs/js/payments/hosted-payment-page)。

## 6. 校验和错误处理

- 字段缺省或显式 null：接受，保存为空；收银台不传 `country_code`。
- 非空值：去除首尾空格后要求符合两个大写英文字母格式；非法值拒绝创建支付单，返回标准参数错误。
- 不对代码是否属于当前 ISO 国家/地区清单做额外维护；具体由 Airwallex 对请求值的接受结果决定。若 Airwallex 拒绝，保留支付单异常并按现有支付失败/待核查流程处理，不静默改成其他国家/地区。
- 同一 `requestId` 重试时，国家/地区字段必须与初次请求相同；更改后返回幂等冲突。

## 7. 配置与迁移

本次实施已同步更新：

- 本地星辙商品模拟数据和创建支付订单请求。
- 签名请求的 DTO、命令对象及集成接口文档。
- 支付单领域对象、数据库实体、持久化映射和新增迁移。
- 幂等请求内容比较。
- Checkout Context 响应、前端 API 类型和 Airwallex.js 初始化调用。
- `AirwallexProperties`、本地/生产配置模板和 `.env.example` 中的固定国家/地区配置。
- 支付链路架构文档及本地模拟契约示例。

不得在本变更中把 `shopperCountryCode` 加到浏览器可控的支付创建接口以绕过星辙订单；付款上下文只能从已创建支付单读取。

## 8. 未包含内容

- 不推断真实星辙正式字段名、来源、国家/地区判定规则或接口签名。
- 不实现 IP 地理定位、国籍识别、地址采集或用户国家/地区选择器。
- 不把国家/地区代码当成商户实体地区、Airwallex 账户地区、结算币种或收单地区。
- 不扩展其他币种、订阅、Adyen 或自建收银台。
- 不改变 Airwallex API Key 权限或服务器认证配置。

## 9. 已确认实施约定

1. 本地星辙订单把金额、币种和可选的 `shopperCountryCode` 一并传给支付服务。
2. 本地样例显式配置 CNY 示例为 `CN`、USD 示例为 `US`，但产品/支付服务不建立币种到国家/地区的通用推断规则。
3. 真实星辙未提供国家/地区时，支付服务省略 Airwallex 的 `country_code`，不使用固定环境变量默认值。
4. 此改动只影响订单上下文和托管收银台参数，不改变业务订单、收款状态、退款和通知职责边界。

本设计方向已由用户确认并进入实施。真实星辙接口字段名称和取值来源仍须取得正式接口资料后适配。
