# 支付软件、模拟业务系统与资金记录设计

## 文档状态

- 状态：待用户审阅。
- 目的：明确独立支付软件、开发模拟系统、模拟支付结果、退款人工执行和资金总览的边界。
- 依据：用户于 2026-10-09 确认：支付软件独立；星辙和付款人均为开发模拟；需要订单历史、退款记录、差异处理和资金总览；退款经核对后由管理员手动确认并发起。
- 外部资料：Airwallex 关于 Payment Intent、退款状态和结算报告的官方说明，见文末。

## 1. 目标与约束

星辙的正式业务系统和 Airwallex 商户账户均由甲方持有。本项目是独立支付服务：接收星辙业务订单，创建或管理收款请求，核实支付/退款状态，通知星辙，并记录运营和资金核对结果。

本地开发需要模拟星辙业务和付款人的行为，验证端到端链路，但模拟系统不进入生产环境。模拟付款结果不代表真实的 Airwallex 收款，不模拟真实钱包余额，也不收集银行卡或账户资料。

当前代码把运营后台和模拟星辙页面放在同一个前端应用里；后端模拟接口受 `local` 配置限制。本设计建议将两个前端改成可独立启动、构建和部署的应用，并继续放在同一代码仓库中管理。

## 2. 应用与责任边界

### 2.1 独立支付软件

生产环境包含支付服务和运营后台，负责：

- 接收星辙的支付、退款指令并校验签名、订单关联、金额、币种和幂等编号。
- 调用 Airwallex 创建收款和退款请求，核验通知、主动查询和服务商状态。
- 可靠通知星辙，记录交易、退款、核查差异、运营备注和审计历史。
- 提供按币种和时间范围查看的支付、退款、费用及结算数据总览。
- 由有权限的员工核对退款并手动确认“发起退款”；退款完成状态仍以 Airwallex 可核实的状态和结算记录为准。

本软件不创建商品、用户钱包或星辙业务订单，不收集付款人的卡片资料，也不决定星辙业务上的退款资格。

### 2.2 本地模拟星辙应用

独立于支付软件前端，仅在开发环境启动，负责：

- 模拟服务目录、用户选购、业务订单创建及订单历史。
- 调用支付软件的本地接口，模拟星辙接收支付/退款状态通知。
- 模拟业务方批准退款并向支付软件发送已批准指令。
- 在订单历史中追加支付、退款申请、退款处理和异常状态记录。

模拟星辙只实现与支付服务联调相关的最小业务，不作为真实星辙合同或生产接口的依据。

### 2.3 本地模拟付款人

付款结果控制只存在于本地开发模拟应用中，开发者可为一笔本地模拟支付选择场景。该控制不出现在生产运营后台，也不伪装成用户的实际银行卡或钱包。

## 3. 建议的工程隔离方式

推荐保留一个 Git 仓库和共享后端支付核心，但将前端拆成两个可独立运行的应用：

- `payment-console`：支付软件运营后台及必要的安全跳转衔接。
- `mock-xingzhe`：本地模拟星辙、模拟订单历史和模拟付款结果控制。

两个应用分别构建和配置不同的本地端口。生产部署只构建支付软件；生产后端不启用模拟星辙控制器、模拟商品、模拟支付结果或模拟退款入口。当前 `/mock-xingzhe` 路由需迁入独立模拟应用，不能只依赖隐藏菜单或页面按钮隔离。

Airwallex 沙盒路径与本地结果模拟路径也必须保持不同来源：

- `AIRWALLEX`：真实调用 Airwallex 沙盒或生产环境，使用服务端凭据和服务商返回状态。
- `LOCAL_SIMULATOR`：只在本地 profile 创建，不调用 Airwallex，不能进入实际收款、退款和结算总额。

## 4. 模拟支付场景与状态

模拟付款人不维护可消费的“账户余额”。通过选择结果场景，模拟支付处理会成功、拒绝或暂时无法确认：

| 开发选择的场景 | 支付项目记录 | 模拟星辙展示 |
| --- | --- | --- |
| 付款成功 | `SUCCEEDED`，写入唯一结果事件和通知 outbox | 收到成功通知后开通示例服务 |
| 付款失败/资金不足 | `FAILED`，失败原因标记为模拟的资金不足 | 显示未付款，服务不开通 |
| 付款处理中 | `PROCESSING`，不写最终成功/失败结果 | 显示等待付款结果 |
| 等待超时/没有收到结果 | `REQUIRES_REVIEW` 或等价待核实状态，不自动改成失败 | 显示结果待确认，服务不开通 |
| 超时后补到最终结果 | 再由开发者选择模拟成功或失败，沿正常状态更新和通知链路推进 | 根据收到的通知更新订单和服务状态 |

同一笔模拟支付的最终结果只能提交一次；待核实订单可在明确的本地模拟控制中补到最终结果。用户刷新或关闭页面不能改变服务端状态。结果通知通过支付服务 outbox 到达模拟星辙，不能由前端直接改订单为已支付。

## 5. 订单历史

模拟星辙提供独立的“我的订单”列表和订单详情。每笔业务订单至少记录：

- 业务订单号、商品/服务名称、金额、币种、创建时间。
- 本地模拟或 Airwallex 沙盒来源，以及关联的支付单号。
- 当前支付状态、业务订单状态、服务开通状态。
- 按时间排列的支付状态变化和通知接收记录。
- 退款申请/批准记录、退款指令编号、支付软件返回状态、退款通知接收记录。
- 需要业务方处理的失败、超时或差异说明。

历史记录是模拟星辙自己的业务记录；支付软件后台则记录支付单、服务商和运营处理事实。两边通过业务订单号、支付单号、退款指令号关联，不共用一份 UI 或把模拟业务记录当成支付账本。

## 6. 退款申请、人工确认和结果回传

建议流程：

1. 模拟用户在模拟星辙订单上提交退款申请；模拟星辙业务方按业务规则批准或拒绝。
2. 只有模拟星辙批准后，才向支付软件发送带稳定指令编号的退款请求。生产中同样由真实星辙决定是否批准。
3. 支付软件验证签名、支付单、原支付状态、币种、金额、剩余可退款金额、重复指令和当前核查结果。
4. 有任何订单、金额、币种、原支付或退款余额差异时，状态转为待处理并显示具体差异；不调用 Airwallex。
5. 核对通过后进入“等待管理员确认”。仅 `STAFF_ADMIN` 可检查证据并点击“确认并发起退款”；系统记录操作人、时间、检查结果和指令编号，再调用 Airwallex。`STAFF_OPERATOR` 可查看并留备注，但不能确认退款执行；项目所有者继续只读。
6. Airwallex 返回或后续通知/查询的退款状态，驱动退款记录更新。管理员不能直接把状态改成“退款成功/已完成”。服务商受理与服务商结算状态分别展示。
7. 支付软件把核实后的退款结果通知星辙。模拟星辙以事件编号去重，并将退款结果追加到原订单历史。
8. Airwallex 结算报告到达后，执行后续资金核对；发现净额、手续费或退款记录差异时创建异常，不倒改原始支付/退款事实。

管理员的人工动作是对“已由星辙业务批准的退款指令”进行支付侧复核并确认执行，不是替星辙批准退款。若核对有异常，管理员应记录处理结论或等待外部证据；不允许通过按钮强行完成退款。

## 7. 支付软件后台总览与资金口径

总览按时间范围和币种筛选；CNY、USD 等币种分别列出，禁止直接相加。建议区分以下指标：

| 指标 | 口径 |
| --- | --- |
| 支付成功金额 | 已由 Airwallex 核实为成功的支付金额；不代表已结算入账 |
| 退款申请金额 | 已收到且尚未终结的星辙退款指令金额 |
| 退款处理中金额 | 已由管理员确认发起，等待 Airwallex 最终处理的金额 |
| 退款已结算金额 | Airwallex 退款状态和结算报告确认的退款金额 |
| 手续费 | 来自 Airwallex 结算/费用报告的服务商费用，不能估算成实际费用 |
| 实际结算入账 | Airwallex 结算记录确认进入商户 Airwallex 余额/结算目的地的金额，按报告状态显示 |
| 待核实/差异 | 支付、退款、服务商状态或结算报告之间暂时不能匹配的记录数及金额 |

总览必须分别展示支付成功额、已退款额和实际结算入账额。不得用“支付成功金额 - 退款金额”伪造实际到账金额，因为结算批次、手续费、保留款、争议和币种转换会影响净额。未来若要显示“转入银行账户的金额”，需要对应的 Airwallex 出账/银行回单来源；不能将 Airwallex 余额入账等同于银行到账。

本地模拟交易不计入生产财务指标。开发环境可以显示独立的模拟统计，但必须带显著“本地模拟”标记，且与 Airwallex 沙盒或生产指标分区展示。

Airwallex 官方资料指出 Payment Intent 为成功状态不意味着资金已经进入 Airwallex 余额；结算报告和交易对账报告分别提供支付、退款、结算和费用核对所需数据。因此，首期总览可先展示已有支付/退款统计，实际结算入账与手续费指标需在接入相应报告后显示，接入前明确显示“待接入”。

## 8. 异常与安全边界

- 超时是状态未知，不自动改成失败，不重复创建新的付款或退款请求。
- 重复退款请求必须使用原指令编号；相同编号但内容不同则拒绝。
- 未匹配、超额、币种不符、服务商查询失败、通知失败和结算差异都要有单独异常状态和处理记录。
- “支付成功”“退款已受理”“退款已结算”“资金已入账”是不同事实，不能互相替代。
- 有权限的员工可核实、重试可重试通知及记录备注；仅 `STAFF_ADMIN` 可确认发起已批准退款。任何角色都不可修改支付成功事实或手工伪造退款完成事实。
- 所有模拟付款控制、模拟退款入口仅开发环境可用；Airwallex 凭据只存在服务端配置，不复制到模拟前端。
- 所有金额以服务端订单和 Airwallex 响应/报告为准；浏览器不能提交或覆盖实际金额、币种、结算金额或退款余额。

## 9. 分阶段实施建议

1. **应用隔离**：把支付运营前端和本地模拟星辙前端拆为两个独立启动/构建入口；保证生产包不含模拟页面。
2. **模拟支付结果扩展**：增加付款失败原因、处理中、超时待核实和超时后补到结果场景；保留 Airwallex 沙盒默认路径。
3. **模拟星辙订单历史**：提供订单列表、详情时间线和退款历史，模拟通知真正驱动业务状态。
4. **退款人工执行**：增加退款待复核、差异拦截、人工确认发起、服务商状态推进和审计；同步模拟星辙记录。
5. **支付总览与真实对账数据**：先基于已有支付/退款事实展示金额；接入 Airwallex 结算和费用报告后再展示实际结算净额、手续费和到账时间。

每阶段开始编码前，补充对应架构细节与实施计划。星辙真实接口、账户权限、退款审批字段、账单报告权限和实际结算目的地仍以甲方及 Airwallex 账户资料为准。

## 10. 待确认事项

- “实际到账”首期需要展示的是进入 Airwallex 商户余额的结算金额，还是 Airwallex 再转入银行账户的金额。当前建议先设计为“Airwallex 结算入账”，银行到账后续有数据源再增加。
- Airwallex 沙盒结算报告及费用报告能否在当前商户沙盒账号获取，需开发阶段确认；不能预先假设沙盒一定产生完整生产格式数据。
- 首期管理后台是仅英文/中文 UI 中的币种本地化，还是需要汇率折算到单一展示币种。当前建议只按币种分别汇总，不做跨币种换算。

## 官方资料

- [Airwallex 支付数据模型](https://www.airwallex.com/docs/payments/about-airwallex-payments/payments-data-model)：Payment Intent 成功与资金进入余额不是同一时点；退款应关联 Payment Intent/Payment Attempt。
- [Airwallex 退款管理与状态](https://www.airwallex.com/docs/payments/manage-payments/refunds)：区分退款已接收、已受理、已结算和失败。
- [Airwallex 支付报表说明](https://www.airwallex.com/docs/payments/manage-payments/reporting)：介绍 Payment Activity、Settlement、Fee、Transaction Reconciliation 等报告的用途。
- [Airwallex Settlement API](https://www.airwallex.com/docs/api/finance/settlements/api)：可查询结算批次金额、状态、结算时间并获取批次报表。
