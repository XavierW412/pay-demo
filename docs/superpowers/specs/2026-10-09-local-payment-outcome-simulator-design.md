# 本地模拟支付结果设计

## 文档状态

- 状态：设计稿，等待用户评审。
- 目的：在开发环境跳过付款人输入，模拟付款结果，联调支付状态处理和星辙通知。
- 不属于正式产品功能，不替代 Airwallex 沙盒验收，不模拟真实资金。

## 1. 已确认目标和边界

- 正式付款由用户在 Airwallex 托管收银台完成；支付项目不开发银行卡输入、绑卡或银行卡资料处理。
- 开发阶段可以实际进入 Airwallex 沙盒托管页，也可以跳过付款人操作，直接模拟付款结果。
- 模拟结果用于观察支付项目状态更新、通知 outbox、模拟星辙去重接收及服务开通链路。
- 模拟支付不能伪装成 Airwallex 交易，不能使用 Airwallex Payment Intent 编号，不能触发真实 Airwallex 查询、退款或结算对账。
- 模拟入口和处理能力仅在 `local` profile 装配；正式环境不提供该接口或页面操作。
- 本设计不增加生产后台的测试支付功能，也不改变生产星辙或 Airwallex 契约。

## 2. 方案比较与选择

### 方案 A：独立本地模拟支付来源（推荐）

本地模拟星辙可在发起支付前选择“Airwallex 沙盒托管付款”或“模拟付款结果”。模拟方式创建带 `LOCAL_SIMULATOR` 来源标识的支付单，不调用 Airwallex。开发者从模拟订单页触发成功或失败结果；服务端使用模拟来源专用状态入口，更新同一支付单并写入现有通知 outbox。模拟星辙继续通过现有签名通知接口接收状态并按成功结果开通示例服务。

优点：覆盖支付项目自己的状态、通知和业务联动；支付来源可辨认；不会制造虚假的 Airwallex 交易。代价：需增加支付来源字段及一个仅本地可用的创建/模拟入口。

### 方案 B：直接修改 Airwallex 沙盒支付单状态

把现有沙盒支付单直接改为成功或失败。

不采用：会让本地模拟状态和真实 Airwallex Payment Intent 混在一起，后续补查可能覆盖模拟状态，退款或对账也可能把它当真实交易处理。

### 方案 C：让模拟星辙直接发送支付成功通知

由模拟星辙跳过支付项目，直接告知自身订单已付款。

不采用：这会绕过被开发的支付项目，不能联调支付单状态、通知 outbox 和失败恢复。

## 3. 推荐流程

1. 开发者在本地模拟星辙创建业务订单，并在首次发起付款前选择付款联调方式。
2. 选择 Airwallex 沙盒时，继续使用当前真实沙盒建单、托管跳转、Webhook/主动查询流程。
3. 选择本地模拟时，支付服务创建 `LOCAL_SIMULATOR` 支付单，不请求 Airwallex，也不返回 Airwallex 付款入口。
4. 本地模拟订单页提供“模拟成功”和“模拟失败”操作。仅未终结的模拟支付单可执行一次结果操作；Airwallex 来源的支付单拒绝该操作。
5. 服务端校验支付来源、支付单状态、业务订单关联、金额和币种；在同一事务内更新内部状态并写入通知 outbox。
6. 现有 outbox 分发器向本地模拟星辙发送签名结果。模拟星辙按事件编号去重；成功时开通示例服务，失败时保留未开通状态。
7. 页面显示“本地模拟结果”，运营交易详情也显示模拟来源。记录不显示 Airwallex 交易编号或已结算信息。

## 4. 数据和状态边界

- `payment_order` 需要可辨认付款来源，建议增加 `payment_provider`：`AIRWALLEX` 或 `LOCAL_SIMULATOR`。存量记录默认归属 `AIRWALLEX`；本地模拟支付明确存为 `LOCAL_SIMULATOR`。
- `provider_payment_intent_id` 对本地模拟支付保持为空；不得构造 `int_...` 等仿真 Airwallex 编号。
- `provider_status` 只存服务商原始状态。模拟支付状态另有明确来源标识，不把 `SIMULATED_SUCCEEDED` 伪装成 Airwallex 原始状态。
- 结果操作只允许一次：`AWAITING_PAYMENT` 可转为 `SUCCEEDED` 或 `FAILED`；成功、失败、取消等终态不得被模拟操作再次改写。
- 本地模拟支付不进入 Airwallex 自动补查、Webhook 匹配或结算对账。
- 对本地模拟支付发起退款必须拒绝，避免误触 Airwallex 退款接口。正式退款沙盒验收继续使用真实 Airwallex 沙盒支付单。

## 5. 接口与页面建议

接口均仅用于本地开发，精确路径以实施计划和现有控制器风格为准：

- 创建模拟支付：由本地模拟星辙明确选择模拟来源后调用；业务订单只能绑定一种付款来源。
- 提交模拟结果：请求字段只允许成功或失败，不接受金额、币种、订单号或服务商编号覆盖。
- 结果操作必须由服务端根据已保存的模拟支付单读取订单编号、金额和币种，不能信任浏览器传值。
- 页面应明确显示“开发模拟”，不与 Airwallex 托管付款按钮混淆。
- 选择付款方式后，不允许同一业务订单切换来源或再创建另一笔支付单；需要另一条演示路径时创建新的模拟业务订单。

## 6. 隔离和防误操作

- 控制器、服务及模拟来源创建能力均限定 `local` profile；生产 profile 不扫描或装配这些组件。
- 正式环境启动保护继续禁止启用星辙模拟器及相关本地配置。
- Airwallex 适配层仅处理 `AIRWALLEX` 支付单；模拟来源不得进入 Airwallex 状态查询、退款或对账适配器。
- outbox 通知只发送到当前环境配置的星辙接收端；本地模拟支付只允许使用本地模拟星辙通知地址。
- 模拟成功只验证本地软件链路，不代表 Airwallex 收款成功、Webhook 已被 Airwallex 调用、生产权限已开通或资金已结算。

## 7. 人工联调验收

1. 本地选择模拟支付后，确认创建支付单时没有 Airwallex API 请求、Payment Intent 编号和托管付款地址。
2. 模拟成功后，确认支付单标记为 `LOCAL_SIMULATOR`，状态变为成功，outbox 生成一条签名通知，模拟星辙只开通一次服务。
3. 模拟失败后，确认通知能送达且模拟星辙不开放服务。
4. 重复提交结果、对 Airwallex 来源订单提交模拟结果、修改金额/币种、对模拟成功订单发退款，均应被拒绝且不调用 Airwallex。
5. 确认运营页面能辨认模拟来源，且模拟支付不出现在 Airwallex 补查和结算对账结果中。
6. 以非 `local` profile 检查模拟接口不可用；现有 Airwallex 沙盒流程与回调逻辑不因模拟模式改变。

## 8. 已知限制

本地模拟只验证支付项目内部状态处理和星辙通知链路，不验证 Airwallex 身份认证、Payment Intent、托管页面、付款方式、Webhook 验签、服务商查询、退款或结算。后续仍需使用 Airwallex 沙盒中实际适用的付款方式分别验证这些服务商边界。

实现时应继续检查 `PaymentStatusApplicationService`、`PaymentOrderProviderUpdateTransaction`、补查任务、退款服务、核查服务、运营列表/详情及模拟星辙通知契约，确保每处都按付款来源做隔离。真实星辙契约仍以甲方正式资料为准。
