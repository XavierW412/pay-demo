# 架构设计文档维护说明

## 1. 为什么按功能逐步写架构

产品说明先确定产品边界和业务目标。架构设计应在具体业务功能准备实现时，根据已知需求、外部接口和技术栈逐步形成，避免在接口和状态尚未知时预先写出看似完整、实际未经验证的系统结构。

本目录只维护已经讨论并准备实现、或已在实现中验证的架构设计。没有真实内容的模块不建立空文件。

当前的支付链路实现记录：[Airwallex 支付创建、结果核实与星辙通知](./payment/payment-flow.md)。设计基线见[本地星辙模拟与 Airwallex 支付链路](../superpowers/specs/2026-10-09-local-xingzhe-airwallex-payment-design.md)，当前付款页调整见[内嵌收银设计](../superpowers/specs/2026-10-09-payment-checkout-experience-design.md)。[星辙付款与通知契约](./integration/xingzhe-payment-contract.md)已在代码中实现但仍属提议，需星辙正式确认或适配后才能作为生产接口。

已实现的后续模块设计：[运营后台](./operations/operations-console.md)、[支付资金总览](./operations/finance-overview.md)、[星辙指令退款执行](./refund/refund-execution.md)、[逐笔支付状态核查](./reconciliation/payment-status-check.md)。支付状态核查与资金总览尚未连接 Airwallex 结算报告，不能当作完整资金结算对账。

跨参与方接口字段、签名方向、幂等、支付/退款状态映射及生产待确认项见[星辙与 Airwallex 支付接口契约](./integration/payment-interface-contracts.md)。星辙相关字段仍是本地模拟/提议契约，不代表甲方生产协议。

## 2. 什么时候新增架构设计

符合以下任一情况时，先写或更新对应设计，再开始实现：

- 新增支付、退款、通知、对账、账号权限等业务模块。
- 改动会影响星辙、Airwallex、前端与后端之间的接口或责任边界。
- 增加状态、重试、并发、幂等、数据迁移或异常恢复规则。
- 技术实现会影响后续扩展、部署、安全或数据可追溯性。

纯文案、局部样式或不改变现有职责和接口的小改动，可直接依据现有规范实施并更新必要说明。

## 3. 文件命名和存放

- 目录名和文件名使用英文小写 kebab-case，正文使用中文。
- 按业务领域组织，不按技术层或日期堆放所有设计。
- 示例：

```text
docs/architecture/
├── README.md
├── payment/
│   ├── payment-initiation.md
│   └── payment-state-machine.md
├── refund/
│   └── refund-execution.md
├── notification/
│   └── starpath-notification-retry.md
└── reconciliation/
    └── settlement-reconciliation.md
```

以上是命名示例。只有讨论到相应功能时再创建文件。

## 4. 架构设计建议内容

根据功能大小选择需要的章节，不要求每份设计机械填满模板：

1. **背景与目标**：为什么要做，成功时能观察到什么结果。
2. **业务边界**：星辙、支付项目、Airwallex 各负责什么；明确不做什么。
3. **主要流程**：正常路径和关键异常路径；必要时使用 Mermaid 时序图或状态图。
4. **模块职责**：前端页面、后端用例、领域模块、外部适配器之间的职责和依赖。
5. **数据与状态**：核心记录、关联标识、状态转换、不可变历史及审计要求。
6. **外部契约**：请求、响应、签名、幂等键、超时和重试；未取得的接口资料标为待确认。
7. **失败恢复**：重复通知、网络超时、状态未知、数据库失败和人工处理路径。
8. **权限与安全**：操作者、权限验证、密钥使用和敏感数据保护。
9. **验证方式**：需要的自动化检查、沙盒联调和人工验收场景。
10. **未决问题与取舍**：列出决策、原因、代价和需向用户/星辙确认的事项。

## 5. 设计与实现保持同步

- 实现前，设计文档中的业务假设和接口状态要经过用户确认。
- 实现中发现设计与真实 Airwallex/星辙协议不符时，先更新设计和产品假设，再继续相关改动。
- 实现完成后，补充实际采用的模块边界、状态和恢复机制；删除已经失效的备选方案。
- 技术选型的全局状态仍以 `docs/engineering/technology-stack.md` 为准；业务需求仍以 `docs/product/product-spec.md` 为准。
- 未核实的接口字段、状态和示例值必须标为“待星辙确认”“建议”或“本地模拟”；Figma 中的原型值标为“原型示例数据（非真实交易）”。不得把原型字段当作外部契约。
- 开发阶段顺序见[开发路线图](../roadmap/development-roadmap.md)。路线图不是已经批准的接口定义，也不替代具体模块的设计和计划评审。
